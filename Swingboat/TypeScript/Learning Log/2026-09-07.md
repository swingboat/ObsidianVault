# TypeScript 学习记录 · 2026-09-07

## 16:13 Biome 配置文件的作用

### 我的问题

项目中的 `biome.json` 文件有什么作用？

### 核心结论

`biome.json` 是 Biome 的项目级配置文件，用来统一代码格式化和静态检查规则。它本身不执行检查；项目脚本通过 `biome check` 读取它。

### 工作原理

配置文件启用了推荐的 linter 规则，并指定了少数规则的例外；formatter 使用 Tab、每级宽度 3、行宽 120。`files.includes` 限定了要检查的 TypeScript 源码、测试和示例，并排除生成文件及依赖目录。

根目录 `npm run check` 会执行 `biome check --write --error-on-warnings .`：`--write` 会自动写回可修复的问题，`--error-on-warnings` 会把警告视为失败。Biome 的格式化和 lint 属于源码检查阶段，不是 JavaScript 运行时行为。

### 在当前项目中的应用

配置位于仓库根目录 `biome.json`；根目录 `package.json` 的 `check` 脚本统一调用它。

## 16:13 `tsconfig.json` 与 `tsconfig.base.json` 的分工

### 我的问题

为什么项目要把 TypeScript 配置拆成 `tsconfig.json` 和 `tsconfig.base.json`？

### 核心结论

`tsconfig.base.json` 保存所有包共用的编译规则，`tsconfig.json` 则是根项目的整体类型检查配置。各个 workspace 还可以基于 base 配置自己的 build/test 配置，避免把不同用途混在一起。

### 工作原理

TypeScript 配置通过 `extends` 继承，子配置可以覆盖父配置。例如 base 中统一设置 `target`、`strict`、模块解析、声明文件和 source map；根 `tsconfig.json` 覆盖为 `noEmit: true`，并加入整个 monorepo 的 `include` 和内部包路径别名，因此只检查类型、不生成文件。

包的 `tsconfig.build.json` 通常设置自己的 `rootDir` 和 `outDir`，把当前包编译到 `dist`；测试配置则设置 `noEmit`，并加入 Vitest 类型。类型配置只影响编译器和编辑器检查，不会在 JavaScript 运行时自动验证数据。

### 在当前项目中的应用

- `tsconfig.base.json`：共享 TypeScript 编译选项。
- `tsconfig.json`：检查 `packages/*/src`、测试和示例，并配置内部包的 `paths`。
- 各包的 `tsconfig.build.json` / `tsconfig.test.json`：分别服务于独立构建和测试类型检查。

## 16:13 Monorepo 与 npm workspaces

### 我的问题

什么是 monorepo？当前项目如何设置和使用它？

### 核心结论

Monorepo（单一代码仓库）是在一个 Git 仓库中维护多个相互关联、可以独立构建或发布的包。它们共享版本控制、依赖安装、工程规范和脚本，但每个包仍有自己的 `package.json`、源码、测试和构建产物。

### 工作原理

根目录 `package.json` 设置 `private: true`，并通过 `workspaces` 声明 `packages/*`、`packages/session-backends/*` 以及若干示例扩展。npm 安装时会识别这些 workspace，并把本地 workspace 包链接起来；发布后，消费者则从 npm registry 安装对应包的版本。

包之间使用 npm 包名引用，而不是依赖相对路径：

```json
{
  "dependencies": {
    "@earendil-works/pi-ai": "^0.85.1"
  }
}
```

源码中仍然使用普通模块导入：

```ts
import * as piAi from "@earendil-works/pi-ai";
```

### 容易踩坑

本地 workspace 链接不等于已经生成了可发布产物。当前项目的构建脚本按依赖顺序先构建底层包，再构建 `coding-agent`；直接跳过依赖包的构建，可能找不到其 `dist` 中的 JavaScript 或声明文件。

### 在当前项目中的应用

核心包包括 `chord`、`tui`、`telemetry`、`ai`、`agent`、`protocol`、`client`、`server`、`coding-agent` 和 SQLite session backend。根目录还统一提供跨包的 `clean`、`test`、`check` 和构建脚本。

## 16:13 Workspace 包的版本维护与相互引用

### 我的问题

Monorepo 中如何维护各个 workspace 包的版本，以及包之间如何引用？

### 核心结论

当前项目对所有可发布包采用锁步版本（lockstep versioning）：它们共享同一个版本号，例如当前均为 `0.85.1`。包之间在 `package.json` 中通过 scoped package name 和版本范围引用；本地开发时解析到 workspace，发布后解析到 npm registry。

### 工作原理

`npm run version:patch`、`version:minor` 和 `version:major` 会让 npm 批量升级 workspace 包，然后运行 `scripts/sync-versions.js`：脚本检查公开包版本是否一致，把内部依赖版本同步到新的版本，并刷新 `package-lock.json`。

标准 SemVer 中，patch 通常表示修复，minor 表示向后兼容的新功能，major 表示破坏性变更。当前项目的发布约定有所不同：patch 用于修复和普通新增，minor 用于破坏性变更，并不使用 major 发布。版本命令本身不会自动完成 changelog、commit、tag 或 npm 发布；正式发布还需要 release 流程。

`^0.85.1` 是版本范围而不是运行时检查。对于 0.x 版本，它通常允许 `0.85.x` 范围内的兼容更新；真正安装哪个版本由 npm 和 lockfile 决定。

### 在当前项目中的应用

`packages/agent/package.json` 声明了对 `@earendil-works/pi-ai`、`@earendil-works/pi-telemetry` 等包的依赖；`packages/coding-agent/package.json` 再组合 `agent-core`、`ai`、`tui` 等包。根目录的版本脚本和 `scripts/sync-versions.js` 负责保持这些内部版本关系同步。

## 22:53 `check:pinned-deps` 为什么要求固定外部依赖版本

### 我的问题

为什么 Pi 要检查依赖是否使用精确版本，而不是直接使用 `^` 或 `~`？

### 核心结论

`check:pinned-deps` 强制外部 registry 依赖使用精确版本，例如 `diff: "8.0.4"`。这样依赖升级必须显式修改 `package.json`，更容易审查，也能减少不同时间安装得到不同依赖版本的风险。

### 工作原理

如果写成 `some-lib: "^1.2.3"`，今天安装可能得到 `1.2.3`，以后重新安装可能得到同一兼容范围内的新版本。新版本即使没有按 SemVer 破坏 API，也可能改变行为、类型定义或构建结果。

根目录的 `package-lock.json` 可以稳定当前仓库的安装结果，但已发布到 npm 的包不会把 Pi 仓库的根 lockfile 带给下游用户。因此，发布包的直接外部依赖仍需在 `package.json` 中固定。

### 容易踩坑

这个检查只约束直接的 `dependencies`、`devDependencies` 和 `optionalDependencies`，不等于所有传递依赖都被写死；传递依赖主要由 lockfile 等安装锁文件管理。固定版本也不代表不需要更新依赖，只是让每次更新都变成明确的代码变更。

### 在当前项目中的应用

`npm run check` 会调用 `node scripts/check-pinned-deps.mjs`。脚本跳过 Pi 自己的 workspace 包，以及 `workspace:`、`file:`、`git:` 等非 registry 依赖；它主要检查外部依赖是否为完整的 `major.minor.patch` 版本。

## 22:53 npm 版本范围符号 `^` 的作用

### 我的问题

既然外部依赖要固定版本，那么 npm 中的 `^` 还有什么作用？

### 核心结论

`^` 表示允许安装满足兼容约束的更高版本，减少手动升级依赖的频率。它表达的是“允许的版本范围”，不是运行时检查，也不保证每次安装得到同一个版本。

### 工作原理

常见范围如下：

```text
^1.2.3  => >=1.2.3 且 <2.0.0
^0.85.1 => >=0.85.1 且 <0.86.0
^0.0.3  => >=0.0.3 且 <0.0.4
```

对于已经有 `package-lock.json` 的项目，当前安装通常会使用 lockfile 中记录的具体版本；`^` 仍然会影响未来更新 lockfile，以及其他用户安装已发布包时可以选择的版本范围。

### 容易踩坑

`^` 的“兼容”依赖库遵守 SemVer 约定。实际项目可能存在未遵守约定的发布，或者类型、构建工具等变化仍然影响使用者，所以不能把 `^` 当成绝对安全的升级保证。

### 在当前项目中的应用

Pi 对内部 workspace 包使用类似 `@earendil-works/pi-ai: "^0.85.1"` 的范围，因为内部包采用锁步版本，并由 `scripts/sync-versions.js` 统一同步。外部依赖则使用精确版本，以兼顾内部包的兼容声明和外部依赖的可复现性。
