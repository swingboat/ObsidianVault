## 09:49 `from __future__ import annotations` 的作用

### 我的问题

模块顶部的 `from __future__ import annotations` 是干什么用的？

### 核心结论

它让所有类型注解**延迟求值**（存成字符串而非在定义时执行），从而消除注解带来的运行时开销，并允许引用尚未定义的类型。

### 工作原理

默认情况下，函数签名里的注解会在模块加载时被真正求值。加上这行 `__future__` 导入后，注解只被保存为字符串，只有在显式调用 `typing.get_type_hints()` 时才解析。

带来两个好处：

- **避免循环导入**：注解里用到的类型不必真的 import 进来（配合 `if TYPE_CHECKING:` 使用）。
- **前向引用无需引号**：可以直接写 `def f() -> MyClass:`，即使 `MyClass` 定义在后面。

### 最小示例

```python
from __future__ import annotations


class Node:
    # 没有 future 导入时必须写成 "Node"（字符串）
    def next(self) -> Node: ...
```

### 容易踩坑

- 依赖运行时读取注解的库（早期 Pydantic、部分 DI 框架）可能因此拿不到真实类型对象，需要它们自己调 `get_type_hints()` 解析。
- 这只影响**注解**，不影响默认值等其他表达式。

## 09:58 `ABC` 抽象基类：强制子类实现接口

### 我的问题

`class Foo(ABC)` 里的 `ABC` 是什么？它起什么作用？

### 核心结论

`ABC` 是 `abc` 模块提供的便捷基类（元类为 `ABCMeta`）。配合 `@abstractmethod`，它能在**实例化时**强制子类必须实现指定方法，否则抛 `TypeError`。

### 工作原理

`ABCMeta` 会收集所有被 `@abstractmethod` 标记的方法名，存进 `__abstractmethods__`。实例化时若该集合非空，直接拒绝创建对象。

它实现了三件事：

1. 强制子类实现约定方法；
2. 定义接口契约（基类只声明不实现）；
3. 禁止直接实例化基类本身。

### 最小示例

```python
from abc import ABC, abstractmethod


class Runner(ABC):
    @abstractmethod
    async def run(self, ctx, stream) -> None: ...


class Bad(Runner):
    pass


Bad()
# TypeError: Can't instantiate abstract class Bad
#            without an implementation for abstract method 'run'
```

### 容易踩坑

- **只有 `@abstractmethod` 标记的方法才被强制**。类体里写 `manifest: SomeType` 这样的纯注解**不会**被强制，子类漏写不会在实例化时报错，而是等到别处访问才抛 `AttributeError`。
- 检查发生在**实例化**时，不是定义子类时。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/core/capability_protocol.py` 用它定义所有能力插件的基类：

```python
class TurnCapability(ABC):
    manifest: CapabilityManifest        # 仅注解，不被强制

    @abstractmethod
    async def run(self, context, stream) -> None: ...
```

这样 orchestrator 可以对任意能力统一 `await capability.run(...)`，无需关心具体类型 —— 典型的多态与依赖倒置。

## 10:05 抽象方法体里为什么写 `...`

### 我的问题

抽象方法既然没有实现，为什么函数体要写一个 `...`？

### 核心结论

`...` 是内置单例 `Ellipsis`，在这里只是**占位符** —— Python 语法不允许空函数体。它已成为"此处故意无实现"的社区惯用信号，但本身不提供任何强制力。

### 工作原理

`def` 后必须至少跟一条语句，否则 `IndentationError`。三种写法都合法：`...`、`pass`、或仅一个 docstring（docstring 本身就是合法语句）。

选 `...` 而非 `pass` 的理由：类型存根文件（`.pyi`）全部使用 `...`，这个约定外溢到了 Protocol / ABC / `@overload` 声明；且可以写成单行，接口密集时更紧凑。

### 最小示例

```python
class Port(Protocol):
    def emit(self, event) -> None: ...      # 必需：这是唯一的函数体


class Base(ABC):
    @abstractmethod
    def run(self) -> None:
        """已有 docstring 作为函数体。"""
        ...                                  # 冗余，纯风格选择
```

### 容易踩坑

`...` **不会**在被误调用时报错。如果子类写了 `super().run()`，函数体会正常执行并返回 `None`，问题被静默吞掉。

若想防护这种情况，应改用：

```python
@abstractmethod
def run(self):
    raise NotImplementedError
```

取舍：`...` 简洁、适合纯接口声明；`raise NotImplementedError` 对"子类误调 super"提供运行时防护。

## 10:08 模块级 `__getattr__`（PEP 562）

### 我的问题

写在模块顶层（不在任何 class 内）的 `__getattr__` 是什么？属于哪个级别的定义？

### 核心结论

这是 **Python 3.7 引入的模块级 `__getattr__`**，在访问模块属性**失败之后**作为兜底被调用。它与类内部的 `__getattr__` 同名但机制完全不同。

### 工作原理

两者的区别：

| | 模块级 | 类级 |
| --- | --- | --- |
| 定义位置 | 模块顶层的普通函数 | class 内部的方法 |
| 签名 | `def __getattr__(name)` | `def __getattr__(self, name)` |
| 触发者 | 模块属性查找失败 | 实例属性查找失败 |
| 引入版本 | Python 3.7 (PEP 562) | 一直都有 |

关键点：**只在常规查找失败后触发**，模块里已存在的名字走正常路径，因此零性能开销。

常见用途：废弃别名、惰性导入（推迟重量级子模块）、动态生成模块常量。

### 最小示例

```python
# mymod.py
def __getattr__(name: str):
    if name == "OldName":
        import warnings
        warnings.warn(
            "OldName is deprecated; use NewName.",
            DeprecationWarning,
            stacklevel=2,      # 指向调用方那一行，而非本文件
        )
        return NewName
    raise AttributeError(name)   # 其他名字必须照常报错
```

### 容易踩坑

- **结尾的 `raise AttributeError(name)` 不可省略**。否则函数隐式返回 `None`，`hasattr()` 会永远为真，IDE 补全和各类内省机制全部失灵。
- `stacklevel=2` 很重要，否则警告指向 `__getattr__` 内部，无法定位真正的调用点。
- 动态属性**不会**出现在 `dir(module)` 中，除非同时实现模块级 `__dir__`。对废弃别名而言，不实现反而是想要的效果。
- 与 `__all__` 配合：把废弃名字排除在 `__all__` 外，`import *` 拿不到它，但显式 import 仍可用 —— 这是"能用但不推荐"的标准表达。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/core/capability_protocol.py` 用它为重命名的基类做软着陆：旧名 `BaseCapability` 仍可导入，但会发出 `DeprecationWarning` 指向新名 `TurnCapability`。若直接写 `BaseCapability = TurnCapability`，就无法插入警告。

## 10:49 `typing.cast` 与参数类型的逆变

### 我的问题

`cast(StreamBus, stream)` 这行代码是什么意思？为什么有些类需要它，有些不需要？

### 核心结论

`cast(T, value)` 是**纯类型标注操作，运行时零行为** —— 源码里就是 `return val`。它不转换、不检查、不抛异常，只用于告诉类型检查器"把它当作 T 看待"。

### 工作原理

需不需要 `cast`，取决于方法签名把参数标注成了**宽接口**还是**具体类**：

- 签名写宽接口（如 `Protocol`），但要把参数传给一个要求具体类的函数 → 类型检查器报错 → 用 `cast` 压制。
- 签名直接写具体类 → 传递时类型天然匹配 → 不需要 `cast`。

### 最小示例

```python
from typing import Protocol, cast


class Port(Protocol):
    def emit(self, e) -> None: ...


class Bus:                      # 比 Port 多出很多方法
    def emit(self, e) -> None: ...
    def content(self, text) -> None: ...


def needs_bus(bus: Bus) -> None: ...


def run(stream: Port) -> None:
    needs_bus(cast(Bus, stream))     # 宽 → 窄，需要 cast
```

### 容易踩坑

- **`cast` 没有任何运行时保护**。断言错了不会报错，只会在后续访问不存在的属性时炸 `AttributeError`。需要运行时校验请用 `isinstance` 或 Pydantic。
- 另一种写法是**在子类签名里直接收窄参数类型**，这样不需要 `cast`，但严格来说违反了**里氏替换原则**：参数应当是**逆变**的（子类接受的类型不应比父类更窄）。mypy 严格模式可能告警。

两种取舍：

| 写法 | 类型学正确性 | 代价 |
| --- | --- | --- |
| 保留宽签名 + `cast` | 合规 | 每处调用多一行 |
| 直接写具体类型 | 逆变违规 | 放弃了替换灵活性 |

### 在当前项目中的应用

`HKUDS/DeepTutor` 中两派写法并存：`deeptutor/capabilities/` 下的能力保留 `StreamBusProtocol` 签名 + `cast`；`deeptutor/agents/` 下的能力直接写 `StreamBus`。属于风格不一致而非缺陷 —— 但若要给测试注入只实现 Protocol 两个方法的假对象，后者会先在类型层面报错。

## 11:20 `Protocol` 结构子类型 vs `ABC` 名义子类型

### 我的问题

同一个文件里既有 `class X(ABC)` 又有 `class Y(Protocol)`，两者该怎么选？

### 核心结论

`ABC` 是**名义子类型** —— 必须显式继承才算数；`Protocol` 是**结构子类型**（鸭子类型）—— 只要方法签名对得上就算实现，无需继承。

### 工作原理

| | `ABC` | `Protocol` |
| --- | --- | --- |
| 关系建立 | 显式继承 | 结构匹配，无需继承 |
| 检查时机 | 运行时（实例化即报错） | 主要靠静态检查器 |
| 典型用途 | 定义**要被实现**的插件基类 | 定义**被依赖**的外部端口 |

经验法则：**"我要求别人实现"用 ABC，"我依赖别人提供"用 Protocol**。后者让调用方无需依赖你的类型定义，测试时可随手传入假对象。

### 最小示例

```python
from typing import Protocol


class Port(Protocol):
    def emit(self, e) -> None: ...


class FakeBus:                 # 完全不继承 Port
    def emit(self, e) -> None:
        print(e)


def run(p: Port) -> None:
    p.emit("hi")


run(FakeBus())                 # 类型检查通过：结构匹配即可
```

### 容易踩坑

- `Protocol` 默认**不支持** `isinstance()`。需要运行时检查必须加 `@runtime_checkable`，且它只检查方法**是否存在**，不检查签名。
- 结构匹配是静态概念，写错方法名时运行时才会暴露。

## 11:31 用返回值而非异常传递校验错误

### 我的问题

一个解析函数为什么返回 `(payload, error)` 元组，而不是直接抛异常？

### 核心结论

当**调用方需要把错误当成正常数据继续处理**（而非中断流程）时，返回 `(结果, 错误)` 元组比抛异常更合适。异常适合"不该发生"的情况，这里错误是预期内的高频事件。

### 工作原理

典型场景是校验来自不可信来源（LLM 输出、用户输入、外部 API）的数据：错误信息需要回传给对方让它自行改正，而不是让整个流程崩溃。

搭配的策略是**"宽进严出"**：能修就修，不轻易拒绝。

### 最小示例

```python
def build(raw: Any) -> tuple[Payload | None, str | None]:
    """成功返回 (payload, None)，失败返回 (None, 错误消息)。"""
    if not isinstance(raw, list):
        return None, "`items` must be an array."
    if len(raw) > MAX_ITEMS:
        raw = raw[:MAX_ITEMS]        # 截断而非报错
    ...
    return Payload(...), None
```

### 容易踩坑

- 这种签名**容易被忽略错误分支**（直接 `payload, _ = build(x)` 然后用 `None` 崩掉）。返回类型要标注成 `X | None`，让类型检查器强制调用方处理。
- 归一化时的"聪明修复"要克制。例如去重时只做**精确匹配**，模糊匹配可能误删合法数据。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/tools/ask_user.py` 是这一模式的完整实例：它把 LLM 生成的不可信 JSON 转成前端可安全渲染的结构。

具体的容错手段值得借鉴：

- 字段别名兼容（`prompt` / `question`、`multi_select` / `multiSelect`）；
- 超长文本截断补 `…`，超量条目直接切片；
- id 缺失自动生成、重复自动加后缀，而非拒绝；
- 用 `frozen=True` 的 dataclass 保证载荷构建后不可变。

只有真正无法挽救的（类型完全不对、必填字段为空）才返回错误消息。
