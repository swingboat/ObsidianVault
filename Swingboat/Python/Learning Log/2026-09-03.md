## 10:56 逻辑运算符 `and` / `or` / `not` 与位运算符 `&` / `|` / `~`

### 我的问题

Python 里"或者"写 `or` 而不是 `|`，那"并且"是不是写 `and`？两者有什么区别？

### 核心结论

是的，"并且"用 `and`，"非"用 `not`。`and` / `or` / `not` 是**逻辑运算符**，带短路求值；`&` / `|` / `~` 是**位运算符**，作用于整数的二进制位，不短路，优先级也更高。

### 工作原理

**短路求值**：`a and b` 中如果 `a` 为假，`b` 根本不会被求值；`a or b` 中 `a` 为真则跳过 `b`。这让下面这种写法是安全的：

```python
if user is not None and user.is_active:  # user 为 None 时不会去取属性
    ...
```

换成 `&` 就会两边都求值，直接 `AttributeError`。

另一个细节：`and` / `or` **返回的是操作数本身而不是布尔值**。`"" or "default"` 得到 `"default"`，这也是 `x = arg or fallback` 这种惯用法的由来（但要小心 `0`、`""`、`[]` 都是假值）。

`&` / `|` 则是按位计算：`6 & 3 == 2`（`110 & 011 = 010`），跟真假判断完全是两回事。

### 容易踩坑

- **优先级**：`&` 比比较运算符 `>` 优先级更高，`a > 0 & b > 0` 会被解析成 `a > (0 & b) > 0`，结果往往不是你想要的。
- **NumPy / pandas 是例外**：布尔数组必须用 `&` `|` `~`，而且每个条件要加括号，因为数组重载了这些运算符；用 `and` 会因为"数组的真值不明确"直接报错。

```python
df[(df.a > 0) & (df.b > 0)]   # 正确
df[df.a > 0 and df.b > 0]     # ValueError: truth value of a Series is ambiguous
```

## 10:59 `*` 解包：`[*seq, x]` 是摊平不是嵌套

### 我的问题

`tools_used=[*SOLVE_TOOL_NAMES, "rag", "reason"]` 里的 `*` 是什么意思？是指针吗？

### 核心结论

`*` 是**可迭代对象解包**（iterable unpacking），把序列里的元素逐个"摊平"进新的容器，跟指针毫无关系。Python 根本没有指针。

### 工作原理

若 `SOLVE_TOOL_NAMES = ("solve_plan", "solve_finish_step", "solve_replan")`，那么：

```python
[*SOLVE_TOOL_NAMES, "rag"]
# 等价于
["solve_plan", "solve_finish_step", "solve_replan", "rag"]
```

没有 `*` 的话会得到嵌套结构 `[("solve_plan", ...), "rag"]`。等价写法是 `list(SOLVE_TOOL_NAMES) + ["rag"]`，但 `*` 更简洁，而且能在一个字面量里混合多个来源。

`*` / `**` 的其他常见位置：

```python
f(*args)                    # 调用时展开成位置参数
f(**kwargs)                 # 调用时展开成关键字参数
{**base, "k": 1}            # 合并字典（右侧覆盖左侧）
def f(*args, **kwargs): ...  # 定义时收集可变参数
first, *rest = [1, 2, 3]    # 解构赋值，rest == [2, 3]
def f(a, *, b): ...          # 裸 * 表示其后必须用关键字传参
```

### 最小示例

```python
def merge(*groups: list[int]) -> list[int]:
    return [x for g in groups for x in g]


merge([1, 2], [3])  # [1, 2, 3]
```

### 容易踩坑

Python 没有指针，但变量**是对象的引用**：赋值只复制引用，不复制对象。所以可变对象会被"共享"。

```python
a = [1, 2]
b = a
b.append(3)
print(a)  # [1, 2, 3] —— a 也变了
```

需要独立副本时用 `list(a)` / `a.copy()`（浅拷贝）或 `copy.deepcopy(a)`。反过来说，`[*tup, ...]` 这种写法总是新建容器，原对象不会被改动，所以是安全的。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/capabilities/solve/capability.py` 中，能力清单把常量元组摊平进声明列表：

```python
tools_used=[*SOLVE_TOOL_NAMES, "rag", "code_execution", "reason"]
```

这样常量本身仍是不可变元组，而每次构造出的是一份新的 list，互不影响。

## 11:11 元组 tuple：不可变的有序序列

### 我的问题

元组到底是什么？Java 里好像没有对应的类型。

### 核心结论

元组是**不可变的有序序列**，用小括号写。它支持索引、切片、遍历，但创建后不能增删改；因为不可变，它还是**可哈希的**，可以当 dict 的 key 或放进 set。

### 工作原理

```python
t = ("solve_plan", "solve_replan")
t[0]            # 'solve_plan'   可以读
t[1:]           # ('solve_replan',)  可以切片
t[0] = "x"      # TypeError      不能改
```

和 `list` 的取舍：

| | `list` | `tuple` |
| --- | --- | --- |
| 字面量 | `[1, 2]` | `(1, 2)` |
| 可变 | 是 | 否 |
| 可哈希 | 否 | 是（元素都可哈希时） |
| 典型语义 | 同类元素的集合 | 结构固定的一条记录 |

语义上的经验法则：list 装"多少个同类东西"，长度可变；tuple 装"一条记录的各个字段"，位置有含义。

多返回值本质就是元组——`return a, b` 返回的是 `(a, b)`，调用方 `x, y = f()` 只是解构。

### 容易踩坑

```python
x = (1)     # 这是 int！括号在这里只是分组
x = (1,)    # 单元素元组必须带逗号
x = ()      # 空元组
a, b = 1, 2  # 括号可省略，右边其实就是元组
```

"不可变"只是浅层的：`([1], 2)` 这个元组里的 list 仍然可以被 append，此时元组也不再可哈希。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/capabilities/solve/tools.py` 用元组声明常量清单，类型注解写明是变长同类元组：

```python
SOLVE_TOOL_NAMES: tuple[str, ...] = (
    "solve_plan",
    "solve_finish_step",
    "solve_replan",
)
```

这是在表达"这是一份不该被修改的常量清单"，作用类似 Java 的 `static final List.of(...)`。

### 相关知识

- Java 长期没有元组，通常用 `record Pair<A, B>(A a, B b) {}`（Java 16+）、`Map.Entry` 或自定义小类替代。
- 想要"元组 + 字段名"时，Python 用 `typing.NamedTuple` 或 `@dataclass(frozen=True)`，这就非常接近 Java 的 `record`：

```python
from typing import NamedTuple


class Point(NamedTuple):
    x: int
    y: int


p = Point(1, 2)
p.x, p[0]  # 具名访问和下标访问都支持
```

## 11:16 `asyncio.create_task` + 异步生成器：让生产与消费并行

### 我的问题

一个长流程的异步任务，怎么做到"一边跑一边把中间结果流式吐给调用方"？

### 核心结论

把长流程用 `asyncio.create_task()` 丢到后台**并发执行**，同时用 `async for` 消费一个事件队列；生产者写队列，消费者读队列，两者互不阻塞。最后必须 `await` 那个 task，才能拿到它的异常。

### 工作原理

关键在于 `create_task` 是**立即调度、不等待**的：它把协程包成 Task 交给事件循环，函数马上往下走。而 `async for event in stream` 会在队列空时挂起，把控制权让回事件循环，后台 Task 才有机会推进。

```python
async def handle() -> AsyncIterator[Event]:
    bus = StreamBus()

    async def _run() -> None:
        try:
            await long_pipeline(bus)      # 期间不断 bus.emit(...)
        finally:
            await bus.close()             # 关闭后 subscribe() 才会结束

    stream = bus.subscribe()              # 先拿到迭代器
    task = asyncio.create_task(_run())    # 再启动后台任务

    async for event in stream:
        yield event

    await task                            # 让 _run 内未捕获的异常在这里抛出
```

三个必须遵守的点：

1. **`finally` 里一定要关闭队列**，否则消费端的 `async for` 永远等不到结束信号，直接死锁。
2. **最后要 `await task`**。不 await 的话，Task 里的异常会被吞掉，只在解释器回收时打印一句 `Task exception was never retrieved`。
3. **要保留 task 的引用**。事件循环只持弱引用，局部变量被回收后任务可能被中途 GC 掉。

### 容易踩坑

- `await coro()` 和 `asyncio.create_task(coro())` 完全不同：前者是"等它跑完"（串行），后者是"让它跑"（并发）。想并发却写成 `await`，是 asyncio 最常见的错误。
- 生成器函数里不能直接用 `return value` 返回结果——`async def` + `yield` 是异步生成器，`return` 只能用来提前结束。结果要通过副作用（写入传入的对象）或事件本身传递。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/runtime/orchestrator.py` 就是这个模式：`ChatOrchestrator.handle()` 是异步生成器，capability 的 `run()` 返回 `None`（所有产出都走事件流），编排层负责在 `finally` 中补发 `DONE` 事件并关闭 bus，异常则被转成一条用户可见的 error 事件。

## 11:16 Pydantic 请求校验：`Literal` + `extra="forbid"`

### 我的问题

怎么让一个配置对象"必须显式传、字段不能多也不能错"？

### 核心结论

用 Pydantic 的 `BaseModel`：`Literal[...]` 把字段限死在枚举值上，`model_config = ConfigDict(extra="forbid")` 拒绝未声明的多余字段，`@field_validator` 做范围钳制。校验失败抛 `ValidationError`，在边界处一次性转成人话错误信息。

### 工作原理

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, field_validator

Depth = Literal["quick", "standard", "deep", "manual"]


class RequestConfig(BaseModel):
    model_config = ConfigDict(extra="forbid")

    depth: Depth                      # 没有默认值 = 必填
    max_iterations: int | None = None

    @field_validator("max_iterations")
    @classmethod
    def clamp(cls, value: int | None) -> int | None:
        return None if value is None else max(1, min(value, 10))
```

三层保护各司其职：

- `Literal` 同时是**类型注解**（mypy 能静态查出拼错的字面量）和**运行时校验**（传 `"fast"` 直接报错）。
- `extra="forbid"` 让字段名打错不再被静默忽略——默认行为 `extra="ignore"` 会把多余键丢掉，出问题很难查。
- `field_validator` 返回**修正后的值**，所以适合做 clamp 这种规范化，而不只是判断合法性。

### 容易踩坑

- `@field_validator` 必须配 `@classmethod`，且顺序是 `field_validator` 在上、`classmethod` 在下。
- 这是 Pydantic **v2** 的写法。v1 里对应的是 `@validator` 和内部 `class Config`，两套 API 不通用。（版本相关，迁移时需确认依赖版本）
- 捕获 `ValidationError` 后建议用 `exc.errors()` 拼出 `字段路径: 原因` 的形式再抛业务异常，比直接把原始异常暴露给用户可读得多。

### 在当前项目中的应用

`HKUDS/DeepTutor` 的 `deeptutor/agents/research/request_config.py` 用这套组合，使 deep research 无法"裸调"：传空配置直接抛 `Deep research requires an explicit config object.`，避免模式和深度悄悄取到默认值。
