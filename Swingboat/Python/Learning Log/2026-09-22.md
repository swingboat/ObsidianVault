## 13:51 Literal：限定字面量取值的类型提示

### 我的问题

`typing.Literal` 在代码里的作用是什么？

### 核心结论

`Literal["a", "b", "c"]` 声明一个变量/类型只能取列出的几个字面量值，供静态类型检查器（mypy/pyright）在开发阶段发现非法赋值；它本身**不做运行时校验**，需要配合 `get_args()` 提取出实际值，再转成 `frozenset`/`set` 才能在运行时做成员判断。

### 工作原理

`Literal` 只是类型提示，Python 解释器执行时会忽略它，就像普通的类型注解一样不会强制检查。项目里常见写法是"一次定义、两处复用"：

```python
from typing import Literal, get_args

AssessmentSource = Literal["deep_question", "mastery_path", "book"]
ASSESSMENT_SOURCES = frozenset(get_args(AssessmentSource))
# 用 ASSESSMENT_SOURCES 做运行时校验：
# if value not in ASSESSMENT_SOURCES: raise ValueError(...)
```

这样避免了手动维护两份重复的字符串列表（一份给类型检查器看，一份给运行时校验用）。

### 容易踩坑

- `Literal` 单独使用时对运行时数据（如从 JSON 解析来的字符串）没有任何保护，容易误以为"声明了就等于校验了"。
- 和 Java 的 `enum` 相比：Java `enum` 是真正的类，JVM 在编译/运行时强制保障合法性；`Literal` 只是字符串+类型提示，运行时保障需要额外手写（`get_args` + 集合判断）。

### 在当前项目中的应用

`deeptutor/core/assessment.py`：`AssessmentSource`/`AssessmentType`/`AssessmentResult` 均用 `Literal` 声明合法取值，再用 `get_args()` 导出对应的 `frozenset` 常量供运行时校验。

## 13:54 frozenset：不可变、可哈希的 set

### 我的问题

`frozenset` 是不是就是"冻住不能修改"的 set？

### 核心结论

是的。`frozenset` 是 `set` 的不可变（immutable）版本：创建后不能再 `add`/`remove`，因此可哈希，可以当字典 key 或塞进另一个 set；成员判断是 O(1) 均摊时间复杂度，比 tuple/list 的线性查找更快。

### 工作原理

- 不可变 → 可哈希 → 能作为 dict key 或 set 的元素（普通 `set` 因为可变，不可哈希，不能这样用）。
- 用在"只读常量集合"场景时，语义上明确表达"这是不该被修改的常量"，防止后续代码误改校验规则。

### 最小示例

```python
ASSESSMENT_SOURCES = frozenset(get_args(AssessmentSource))
if value not in ASSESSMENT_SOURCES:
    raise ValueError(f"invalid source: {value}")
```

### 在当前项目中的应用

`deeptutor/core/assessment.py` 用 `frozenset(get_args(...))` 把 `Literal` 声明的合法值集合转成运行时可查的常量集合。

## 14:06 Pydantic：运行时数据校验 + 类型定义库

### 我的问题

`ConfigDict` 和 `Dict` 有什么区别？Pydantic 是什么、主要做什么用的、为什么需要它？它是不是类似 TypeScript 的 Zod？

### 核心结论

Python 的类型注解（包括 `Literal`、普通 `def f(x: str)`）**只是给人和工具看的静态提示，运行时完全不检查**——这正是需要 Pydantic 的原因。Pydantic 通过继承 `BaseModel` 声明字段类型，在**实例化时自动校验并转换外部数据**（HTTP 请求体、JSON 文件、用户输入等），把"静态类型提示"和"运行时强校验"合二为一，定位上非常接近 TypeScript 的 Zod。`ConfigDict` 不是普通字典类型，而是 Pydantic 提供的**模型行为配置对象**，赋值给 `model_config` 类属性，例如 `ConfigDict(extra="forbid")` 表示"输入数据里出现未声明字段就直接报错"。

### 工作原理

**1. 为什么类型注解在运行时没有保障**

```python
def greet(name: str) -> str:
    return "Hello " + name

data = json.loads(request_body)   # data 类型未知，取决于外部输入
greet(data["name"])               # 若 data["name"] 是 int，Python 不会在这里报错
```
mypy/pyright 只能检查你自己写的代码内部调用是否类型一致；`json.loads` 返回的数据类型是 `Any`，编译期根本不知道其真实结构，Python 解释器执行时也完全忽略 `name: str` 这行注解——直到内部逻辑因类型不对崩溃（或者更糟，静默产生错误结果）才会暴露问题。TypeScript 同理：类型信息在 `tsc` 编译成 JS 后被完全擦除，运行时不再检查。

**2. Pydantic 如何补上这个缺口**

```python
from pydantic import BaseModel, ConfigDict

class LLMSelection(BaseModel):
    model_config = ConfigDict(extra="forbid")
    profile_id: str
    model_id: str

user = LLMSelection(**json.loads(request_body))
# 若字段类型不对或多了未声明字段，这一行直接抛 ValidationError
```
`BaseModel` 是最常用的校验入口，但不是唯一方式：
- `TypeAdapter(list[int]).validate_python([...])` —— 校验任意类型，不必写 class
- `@validate_call` —— 直接给普通函数参数加运行时校验
- `@pydantic.dataclasses.dataclass` —— 给标准库 `dataclass` 加校验能力

**3. `extra` 配置的三种取值**

- `"ignore"`（默认）：多余字段直接丢弃
- `"allow"`：多余字段保留在实例上
- `"forbid"`：多余字段直接报 `ValidationError`

用在校验"外部请求体"的模型上时选 `forbid`，能在字段名拼错（如 `questionId` 而不是 `question_id`）时立刻报出明确错误，而不是被 `ignore` 静默丢弃、之后因缺少必填字段报出令人困惑的错误。

### 容易踩坑

- 不要把 `ConfigDict` 当成"字典类型注解"——它和 `Dict[str, str]` 完全是两回事，前者是 Pydantic 模型的配置对象（本质是 `TypedDict`），后者才是普通的字典类型标注。
- Pydantic 的校验能力不仅限于 `BaseModel`：对单个值/简单容器/函数参数用 `TypeAdapter`/`validate_call` 更轻量，不必事事都定义 class。

### 在当前项目中的应用

`deeptutor/core/turn_request.py` 里几乎每个请求体模型（`LLMSelection`、`OutgoingAttachment`、`NotebookReference` 等）都统一写了 `model_config = ConfigDict(extra="forbid")`，作为该文件对所有外部输入模型的一致约定，确保 WebSocket/CLI 传入的 turn 请求结构不被拼写错误或多余字段污染。
