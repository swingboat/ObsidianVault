# Python 学习记录 · 2026-09-28

## 10:49 用空 `__init__.py` 包把非 Python 静态资源纳入打包

### 我的问题

为什么要建一个只含 `__init__.py` 的 `deeptutor_web` 目录？这样做是不是为了让静态资源也能被打包工具找到和搬运，Python 解释器是不是因此也能"解析" HTML/JS 文件了？

### 核心结论

`__init__.py` 本身不含业务逻辑，唯一作用是让该目录成为**合法的 Python 包**，从而借用 Python 包系统的两项能力：① `import` 机制可以定位到它在磁盘上的安装路径；② 打包工具（setuptools）能按包为单位收集非 `.py` 静态文件一起分发。Python 解释器并不会因此获得解析 HTML/JS 的能力，这些文件对 Python 来说始终是不透明的数据，真正执行它们的是外部的 Node.js 进程（通过 `subprocess` 拉起）。

### 工作原理

- 只有位于"合法 Python 包"目录下的文件，才能被 `pyproject.toml` 里 `[tool.setuptools.package-data]` 声明的规则（如 `deeptutor_web = ["**/*", ".next/**/*"]`）以及 `MANIFEST.in` 的 `recursive-include` 规则收集进最终的分发包（wheel/sdist）。
- 运行时代码可以用 `import deeptutor_web` 后取 `Path(deeptutor_web.__file__).parent` 得到该包在当前环境（venv/conda/全局）中的安装路径，而不需要在代码里硬编码或猜测相对路径。
- 源码开发环境下这个目录通常是空的（只有 `__init__.py`），发布构建时 CI 会把 `next build` 产出的 `server.js`、`.next/static`、`public` 等文件复制进去；运行时代码会先检查这些文件是否存在，不存在则 fallback 到仓库里的 `web/` 源码目录。

### 最小示例

```python
# deeptutor/runtime/launcher.py（简化）
def _packaged_web_dir() -> Path | None:
    try:
        import deeptutor_web
    except ImportError:
        return None
    path = Path(deeptutor_web.__file__).resolve().parent
    return path if (path / "server.js").exists() else None
```

### 容易踩坑

- 容易误以为"打包进 Python 包"意味着"Python 能执行/解析这些文件"，实际上只是文件的物理搬运和路径定位，语义解析仍由对应运行时（这里是 Node.js）负责。
- 忘记同时配置 `package-data`/`MANIFEST.in`，即使目录下有 `__init__.py`，静态资源也不会被自动打进 wheel。

### 在当前项目中的应用

`HKUDS/DeepTutor` 仓库：`deeptutor_web/__init__.py` 是前端 Next.js standalone 产物的容器包；`deeptutor/runtime/launcher.py` 的 `_packaged_web_dir()` 负责定位，`pyproject.toml`（约 323 行）和 `MANIFEST.in` 负责声明打包规则。

## 10:49 setuptools、wheel、sdist 是什么

### 我的问题

setuptools 和 wheel 分别是什么？sdist 和 wheel 有什么区别？和 Java/Maven 的 `pom.xml`、jar/war 类比是否成立？

### 核心结论

**setuptools** 是 Python 的构建后端（build backend），负责按 `pyproject.toml` 里的声明发现包、收集静态资源、生成元数据并打包。**wheel（`.whl`）** 是预构建好的二进制分发格式，`pip install` 时直接解压即用，不需要在目标机器上重新构建。**sdist（`.tar.gz`）** 是源码分发格式（sdist = **s**ource **dist**ribution），只含原始源码和构建脚本，安装时会在本机重新走一遍构建流程。

### 工作原理

- `pyproject.toml` 的 `[build-system]` 段声明 `requires = ["setuptools>=61.0", "wheel"]` 和 `build-backend = "setuptools.build_meta"`，告诉 pip 用什么工具构建这个项目。
- `[tool.setuptools.packages.find]` 让 setuptools 自动发现哪些目录是 Python 包（含 `__init__.py`）；`[tool.setuptools.package-data]` 声明包内哪些非 `.py` 文件也要打包进去。
- 执行 `python -m build` 会同时生成 `dist/xxx.tar.gz`（sdist）和 `dist/xxx-py3-none-any.whl`（wheel）；`bdist` 是 Binary Distribution 的统称，wheel 是目前最主流的 bdist 具体格式（历史上还有已过时的 `bdist_egg`）。
- 与 Java/Maven 的类比：`pyproject.toml` ≈ `pom.xml`（装配图纸）；setuptools ≈ Maven（构建工具）；wheel ≈ jar/war 或 Maven 发布的 `-bin.tar.gz`（预构建产物，解压即用）；sdist ≈ Maven 发布的 `-src.tar.gz` 源码包（需要本机重新构建）。一个关键差异：Java 的 jar 里是编译后的 `.class` 字节码，而 Python 的 wheel 里通常就是原始 `.py` 源码本身（Python 是解释执行），wheel 的"预构建"价值主要在于跳过了 `package-data` 收集、C 扩展编译等耗时步骤，而非字节码翻译。

### 容易踩坑

- 误以为 wheel 一定经过"编译"，对纯 Python 包而言更准确的说法是"打包排列整理完毕"；只有含 C/C++ 扩展的包，wheel 里才会有真正编译好的平台相关二进制文件。
- 混淆 sdist 和 wheel 的适用场景：如果项目有需要本地编译的 C 扩展，安装 sdist 会触发本机编译（类似 Maven 需要本地工具链），而对应平台的 wheel 则已经编译好，安装更快更省事。
